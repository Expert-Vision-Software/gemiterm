1. Deepen the Cookie Session module

Strong in-process

Files

src/services/auth-service.ts src/services/cookie-storage-service.ts src/services/cookie-monitor.ts src/infrastructure/storage.ts src/services/gemini-client-wrapper.ts

Problem

The cookie lifecycle is scattered across five modules with triple-duplicated validation logic, a 7-day freshness threshold that conflates the months-long __Secure-1PSID clock with the ~600 s __Secure-1PSIDTS rotation cadence, and no active rotation — only passive refresh after API calls. This is the architectural root of the recurring phantom auth bug.

Solution

Collapse into a single CookieSession module behind one interface: ensureSession(profile). It owns proactive RotateCookies POST, two-tier cookie validation (primary + secondary bindings), a typed recovery ladder, and an injectable clock for testability.

2. Remove the Mediator layer

Worth exploring in-process

Files

src/core/mediator.ts src/core/command-handlers.ts src/core/query-handlers.ts src/cli/index.ts

Problem

A CQRS mediator with 12 handler classes, ~20 payload/result interfaces, and 93 lines of wiring serves a CLI with 13 commands. The send() method has no middleware pipeline, no logging, and no multiple transports. Four handlers receive null as any for their service dependencies — they are registered but broken. Two commands (auth, status) bypass the mediator entirely and instantiate services directly, confirming the abstraction earns no leverage.

Solution

Delete the mediator, handlers, and message types (~410 lines). Commands call GeminiClientService and ProfileManager directly. A thin CommandContext holds the resolved services — passed to each command's execute() as a single typed object.

  • + Interface shrinks: commands depend on 1 context, not mediator + PAA
  • + Testability unchanged: same mock points, fewer hops

3. Extract shared Command arg-parsing

Worth exploring in-process

Problem

~285 lines of copied for/switch arg-parsing loops across 8 command files. Every command reimplements the same manual iteration pattern. showUsage() is duplicated ~8 times with identical chalk.bold/padEnd formatting (~100+ lines). 4. Replace hand-rolled terminal input with @inquirer/input

Speculative in-process

Files

src/cli/utils/prompts.ts

Problem

text() (prompts.ts:82-199) is 118 lines of hand-rolled raw terminal input — manual ANSI escape handling, multi-byte UTF-8 decoding, backspace logic, a hardcoded Ctrl-C handler. It reimplements what @inquirer/input already provides. The raw ANSI parser handles Delete (\x1b[3~) but not Home, End, or arrow keys — making the input fragile. @inquirer/prompts is already in the codebase.

Solution

Replace the 118-line text() with a thin wrapper around @inquirer/input, configured with the same shared theme and abort signal used by confirm() and select(). If the inquirer renderer can't match the inline validation rendering, keep a minimal decorate-validate layer on top — but the raw byte loop goes.

Before — raw ANSI parsing (118 lines)

if (byte === 0x03) { cancel(); return; } // Ctrl-C
if (byte === 0x0d || byte === 0x0a) { ... } // Enter
if (byte === 0x08 || byte === 0x7f) { ... } // Backspace
if (byte === 0x1b) { // escape sequence
  if (next === 0x5b && next2 === 0x33) { // Delete
    i += 3; continue;
  }
  i += 1; continue;
}
// multi-byte UTF-8: 0xC0-0xFD range branches...
stdin.setRawMode(true); // manual TTY management
stdin.removeListener("data", onData); // manual cleanup
No Home, End, ↑, ↓, ←, → support

After — @inquirer/input (~20 lines)

import { input } from "@inquirer/prompts";

async text(opts: TextOptions): Promise<string> {
  try {
    return await input({
      message: opts.message,
      default: opts.default,
      theme,
      validate: opts.validate,
    }, { signal });
  } catch (e) {
    throw mapCancellation(e);
  }
}
Arrow keys, Home, End, paste, multi-line — all free with @inquirer/input
  • + Delete ~100 lines of manual byte parsing
  • + Leverage: cursor keys, Home, End free from @inquirer
  • + Locality: input behavior lives in @inquirer, not prompts.ts
  • + Risk: inline validation rendering may need a decorate layer

5. Consolidate Gemini client construction

Worth exploring in-process

Files

src/cli/index.ts src/services/gemini-client-wrapper.ts src/services/profile-auth-manager.ts

Problem

The client construction lifecycle is split across three modules: setupMediator() in cli/index.ts:56-75 (lazy factory + cookie loading), GeminiClientService.constructor (wrapper.ts:96-110, SDK instantiation), and forProfile() (wrapper.ts:209-222, per-profile instantiation). The setupMediator() function creates a separate "factory client" with dummy credentials (secure1psid: "") just to satisfy ProfileAuthManager's dependency. The inline adapter objects (index.ts:84-123) clone the same delegation methods 5 times.

Solution

A single GeminiClientFactory module: createClient(profile) → GeminiClient. It owns cookie loading, SDK construction, init lifecycle, and metadata storage wiring. If the mediator stays, the factory replaces the lazy closure + inline adapters. If the mediator goes, commands call it directly.

Top recommendation

#1 — Deepen the Cookie Session module

This directly addresses the recurring phantom auth bug. The scattered cookie lifecycle — with its 7-day threshold conflating different cookie timers, no proactive rotation, and duplicated validation — is the root cause of "models() works but listChats returns 0." Introducing active RotateCookies POST, two-tier validation, and a recovery ladder into a single deep module pays off on every caller. The other candidates (mediator removal, arg parsing, terminal input, client construction) are independent cleanups that compound the deepening's leverage.
