1. Deepen the Cookie Session module

Strong

Files

src/services/auth-service.ts src/services/cookie-storage-service.ts src/services/cookie-monitor.ts src/infrastructure/storage.ts src/services/gemini-client-wrapper.ts

Problem

The cookie lifecycle is scattered across five modules with triple-duplicated validation logic — the COOKIE_EXPIRY_THRESHOLD_MS constant (7 days) is defined identically in three files: cookie-storage-service.ts:5, gemini-client-wrapper.ts:69, and storage.ts:14 (revalidated at v2.4.2). Validation (validateCookies) and expiry checking (checkCookieFreshness) are duplicated between CookieStorageService and module-level functions in storage.ts, and three different expiry computations coexist: storage.ts:25 takes the max over both __Secure-1PSID* cookies, while cookie-storage-service.ts:68 and auth-service.ts:187 read __Secure-1PSIDTS only. The SDK's live jar and GemiTerm's persisted state have no transactional sync boundary — persistence is the wrapper's persistRefreshedCookies() scattered across 7 internal call sites, while AuthService writes storage directly (auth-service.ts:155) with no validation at all. Cookies are only refreshed passively after successful API calls — there is no proactive rotation. This is the architectural root of the recurring phantom auth bug ("models() works but listChats returns 0").

Solution

Collapse into a single CookieSession module behind one interface: ensureSession(profile) — the only load path — and commit(liveJar) — the only persistence path, forming a transactional jar↔disk boundary (read persisted → merge jar → validate → write) so the SDK's live cookie jar and stored cookies can never diverge. Every writer (API-call refresh, auth-flow capture, rotation response) goes through the same commit; every reader gets cookies validated at commit time. The module owns proactive RotateCookies POST — implemented in-repo, since gemini-web-sdk exposes no rotation API (it only passively absorbs Set-Cookie headers into its public jar) — plus two-tier cookie validation (primary + secondary bindings), a typed recovery ladder, and an injectable clock for testability. The module hides all cookie-name magic strings, freshness thresholds, and persistence details.

2. Deepen the Profile Lifecycle module

Landed 2026-08-14-refactorings-phase2-01-profile-lifecycle-module

Files

src/cli/commands/auth-command.ts src/cli/commands/status-command.ts src/services/auth-service.ts src/services/profile-service.ts src/infrastructure/storage.ts

Problem

After mediator removal and arg-parsing consolidation (refactorings #2, #3), most commands share a clean CommandContext. But auth-command.ts (443 lines) and status-command.ts (59 lines) still use the service locator pattern — they new their own CookieStorage, ProfileManager, PlaywrightCliDriver, and AuthService inline. Profile listing logic (listProfiles + table formatting) is duplicated between auth (lines 173–192) and status (lines 43–46). The ProfileService class is a thin pass-through delegating to ProfileManager — it's a shallow module that adds no depth. CRUD operations (create, list, rename, delete, set-default, show status) are spread across two command files with different instantiation patterns.

Solution

Introduce a single ProfileLifecycle module behind the interface manageProfiles(action, params) — an action-dispatch pattern parameterized on a union type ('list' | 'create' | 'delete' | 'rename' | 'set-default' | 'status'). The module owns all profile I/O, cookie validation for auth status, default-profile marker management, and the login browser flow (delegating to AuthService internally). Both auth-command.ts and status-command.ts become thin adapters that call context.profileLifecycle.manageProfiles(...).

3. Deepen the Chat Output Pipeline

Landed 2026-08-14-refactorings-phase2-04-chat-output-pipeline

Files

src/cli/commands/list-command.ts src/cli/commands/fetch-command.ts src/cli/commands/export-command.ts src/cli/commands/export-all-command.ts src/infrastructure/formatters.ts src/infrastructure/io.ts

Problem

After mediator removal and arg-parsing consolidation, four commands (list, fetch, export, export-all) each implement the same "fetch data → format → write" pipeline. The writeOutput helper is duplicated verbatim between list-command.ts:149-152 and fetch-command.ts:126-129 (3 identical lines). Sort logic is duplicated between list-command.ts:98-112 and prompts.ts:306-325. Date-filter logic is duplicated between list-command.ts:114-129 and export-all-command.ts:127-132. The format-then-write sequence (formatChatAsMarkdown(...) + writeTextFile + console.log) is structurally identical across three commands. These are all shallow adapters — each command knows too much about how to transform and render data.

Solution

Introduce a ChatOutput module with the interface render(data, sink) where data is a typed union (ChatList | Conversation | BatchExport) and sink is { format, out? }. The module owns all formatting strategies (table rendering, markdown export, JSON export), sort/filter logic, and the "write to stdout or file" dispatch. Commands become thin adapters that fetch data then call output.render(data, { format, out }).

4. Deepen the Interactive Chat Session

src/cli/utils/interactive-prompt.ts src/cli/utils/long-arg-guard.ts src/cli/utils/prompt-file.ts src/cli/commands/new-command.ts src/cli/commands/continue-command.ts

Problem

After #4's @inquirer/input replacement, interactive-prompt.ts is a clean 72-line REPL loop. But the split between interactive and non-interactive modes forces every chat command (new, continue) to implement the same "check for interactive flag, if so call interactive loop, else call a one-shot" branching pattern. The spillover-to-temp-file flow (continue-command.ts:84-115 and new-command.ts:61-93) is a verbatim 30-line duplicate — it's the only remaining exact-duplicate code block after arg-parsing consolidation (#3). The invokeListCommand pattern (dynamic import + new CommandRegistry + execute) appears in 3 places. The interactive/non-interactive mode branch is structural duplication — both paths must handle the same concerns (arg-length guard, prompt-file, message extraction) but do so separately.

Solution

Introduce an InteractiveSession module with the interface startChat(params) where params carries the initial message (if any), profile, conversation ID (for continue), prompt file, and mode ('once' | 'repl'). The module owns the spillover-to-temp-file flow, arg-length guard, prompt-file loading, and the REPL loop. new-command.ts and continue-command.ts become thin adapters — they extract params from their arg-specs and call context.interactiveSession.startChat(params).

5. Extract Idempotent Export as a strategy seam

Landed 2026-08-14-refactorings-phase2-03-export-strategy-seam

Files

src/cli/commands/export-command.ts src/cli/commands/export-all-command.ts src/infrastructure/formatters.ts

Problem

export-command.ts and export-all-command.ts each independently implement the "format then write" pattern. export-all adds progress reporting, batch iteration, error collection, and index-file generation — all inside the command class. The format decision (markdown vs json) is hardcoded in formatters.ts as two functions with different signatures (formatChatAsMarkdown takes 4 params, formatChatAsJson takes 2). The filename sanitization logic (export-all-command.ts:134-142) and default filename logic (export-command.ts:103-107) are similar but not identical — each implements its own filename strategy. There is no seam for swapping export strategies; adding a new format would touch both command files and the formatters module.

Solution

Introduce an ExportStrategy adapter interface: export(conversation, format, options) → ExportResult. Implement two adapters: SingleExport (one conversation → one file) and BatchExport (many conversations → directory with index). The formatters module becomes internal to the strategy — each adapter picks the right formatter by format type. export-command.ts and export-all-command.ts become thin adapters that inject the right strategy via CommandContext. This is the "two adapters = real seam" principle: SingleExport and BatchExport are real variant implementations behind the same interface.

Remaining recommendation (sole candidate left)

#1 — Deepen the Cookie Session module

This directly addresses the recurring phantom auth bug. The scattered cookie lifecycle — with its 7-day threshold conflating different cookie timers, triplicate constants, duplicated validation, three divergent expiry computations, no transactional jar↔disk boundary, and no proactive rotation — is the root cause of "models() works but listChats returns 0." Introducing a single deep module with ensureSession(profile) as the only load path, a transactional commit() as the only persistence path, active in-repo RotateCookies POST, two-tier validation, and a recovery ladder pays off on every caller.

The four sibling candidates have all landed and are archived: ProfileLifecycle (#2) removed the last service-locator pattern; InteractiveSession (#4) eliminated the last exact-duplicate code block; ExportStrategy (#5) and ChatOutput (#3) consolidated the output pipeline behind tested seams. Their landing compounds #1's payoff — every caller is now a thin adapter over a CommandContext, so ensureSession(profile) slots into an already-clean seam. An OpenSpec change proposal (openspec/changes/refactorings-phase2-05-cookie-session/) has been drafted for a later implementation session.
